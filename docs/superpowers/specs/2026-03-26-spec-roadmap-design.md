# Design: Spec Roadmap & Split Detection

> **Date:** 2026-03-26
> **Status:** Draft
> **Scope:** 3 commands modified (init, specify, propose) + 1 template added

---

## Problem

LiveSpec lacks a persistent backlog of specs to build. Two gaps:

1. **Post-init blindness:** After `/spec.init`, the user knows the vision and stack but has no structured view of which specs are needed to reach a working product. `/spec.propose` can infer suggestions, but they're ephemeral (read-only, not saved).

2. **Split loss:** When `/spec.specify` receives a request covering multiple independent features, Step 1.5 proposes splitting — but deferred items vanish. The user loses context and intent for the parts not immediately specified.

Both gaps are solved by a single persistent artifact: `.specs/roadmap.md`.

---

## Design

### 1. New Artifact: `.specs/roadmap.md`

A persistent, auto-maintained file with three tiers and a deferred section.

**Template** (`system/templates/roadmap-template.md`):

```markdown
# Roadmap

> Auto-generated by `/spec.init` — updated by `/spec.specify` and `/spec.propose`.
>
> Last updated: YYYY-MM-DD

---

## MVP

<!-- roadmap:mvp:start -->
<!-- roadmap:mvp:end -->

> No items yet.

---

## Post-MVP

<!-- roadmap:postmvp:start -->
<!-- roadmap:postmvp:end -->

> No items yet.

---

## Future

<!-- roadmap:future:start -->
<!-- roadmap:future:end -->

> No items yet.

---

## Deferred

> Items split from `/spec.specify` requests — context preserved for later specification.

<!-- roadmap:deferred:start -->
| Source | Item | Context | Added |
|--------|------|---------|-------|
<!-- roadmap:deferred:end -->

---

*Maintained automatically by LiveSpec commands. Do not remove section markers.*
```

**Item format in tiers:**

```markdown
- [ ] **Feature name** — short description · Roles: X, Y · Scope: S/M/L · Deps: feature-a, feature-b
```

**When a spec is created** via `/spec.specify`, the item is checked and linked:

```markdown
- [x] **User auth** — signup, login, password reset · Roles: All · Scope: M · Deps: none → [001-user-auth](features/001-user-auth/spec.md)
```

**Deferred item format** (table row):

```markdown
| `/spec.specify "auth + audit"` | Audit trail | Track all admin actions with timestamps, exportable logs. Roles: Admin. Scope: S | 2026-03-26 |
```

### 2. Init Phase C — Step 3.9: Generate Roadmap

Inserted between Step 3.8 (testing/strategy.md) and Step 3.10 (README.md).

**Logic:**

1. Read `project.md` — extract roles, vision, real-time needs, scale
2. Read `constitution.md` + `_default.md` — understand stack capabilities
3. Infer expected feature domains using this matrix:

| Signal from project profile | Expected domain |
|---|---|
| Any project with users | Authentication (signup, login, password reset) |
| Multiple roles with different access | Role management / RBAC |
| Role has "post", "create", "manage" actions | CRUD for that entity |
| Real-time messaging mentioned | Messaging system |
| Real-time notifications mentioned | Notification system |
| "Search", "browse", "discover" in vision | Search & discovery |
| "Pay", "invoice", "billing", "monetize" | Payments / billing |
| Admin role exists | Admin dashboard |
| "Mobile" or "responsive" mentioned | Mobile-optimized views |
| "Analytics", "reports", "metrics" | Reporting & analytics |
| "Settings", "preferences", "profile" | User settings / profiles |

4. Classify each inferred feature into tiers:
   - **MVP**: Features required for core value proposition + auth + primary entity CRUD
   - **Post-MVP**: Enhancement features (search, notifications, analytics, admin tools)
   - **Future**: Nice-to-have (advanced analytics, integrations, i18n)

5. Estimate scope per item:
   - **S**: single entity, few stories (settings, preferences)
   - **M**: 1-2 entities, standard CRUD + some logic (auth, messaging)
   - **L**: multiple entities, complex workflows (payments, bidding system)

6. Infer dependencies:
   - Everything depends on auth (if present)
   - Messaging depends on user profiles
   - Payments depend on core entity CRUD
   - Admin dashboard depends on the features it moderates

7. Generate `.specs/roadmap.md` from template
8. Present roadmap summary in Phase C output

### 3. Specify Step 1.5 — Enhanced Split Detection

Replace the current Step 1.5 bullet 1 with a full protocol:

**Step 1.5 — Scope Analysis & Split Detection**

1. **Extract functional domains** from input:
   - Each action verb + object = 1 candidate domain
   - Junction words ("and", "with", "plus", "also", "et aussi") signal boundaries
   - Example: "auth with SSO, role management, and audit trail" → 3 domains

2. **Test independence** — two domains are independent if:
   - They serve different user stories (different actors or goals)
   - They can be delivered and tested separately
   - They touch different primary entities

3. **Evaluate complexity** — flag if combined request would produce:
   - More than 5 P1 user stories
   - More than 3 distinct primary entities
   - More than 8 acceptance criteria

4. **If split detected** (≥2 independent domains OR complexity exceeded):

   ```
   🔀 Split detected — your request covers multiple independent areas:

   | # | Domain | Scope | Independent? |
   |---|--------|-------|-------------|
   | 1 | Auth + SSO | M | — (core) |
   | 2 | Role management (RBAC) | M | Yes |
   | 3 | Audit trail | S | Yes |

   Proposal: I specify **Auth + SSO** now.
   The others go into the roadmap for next specifications.

   → OK? Or do you prefer to keep everything together?
   ```

5. **User accepts split:**
   - Proceed with domain #1
   - Add remaining domains to `.specs/roadmap.md` Deferred section
   - If a domain matches an existing unchecked roadmap item, update that item's context instead of duplicating

6. **User declines split:**
   - Proceed with full request as single spec (current behavior)

7. **Max 2 clarification questions** then proceed with `[ASSUMED]` markers (unchanged from current Step 1.5)

### 4. Specify Step 7.7 — Roadmap Sync

New step after Step 7.6 (changelog update):

1. Read `.specs/roadmap.md` (if it exists; if not, skip silently)
2. Search all tier sections for an unchecked item matching the new feature (fuzzy match on name/description)
3. If match found: check the checkbox + append spec link
4. If split was performed in Step 1.5: add deferred items to Deferred table
5. Update the `Last updated` date
6. Remove `> No items yet.` hint from the tier if it now has items

---

### 5. Propose — Deferred Awareness

Enhance Step 3 (Read Roadmap):

- Also read the Deferred section
- Deferred items are **high-context candidates** — they have user intent captured
- In Step 5 (ranking), deferred items get a +1 priority boost (user already expressed intent)
- When presenting a deferred proposal, include origin:
  > *Originally split from: `/spec.specify "auth + audit"` — "Track all admin actions with timestamps, exportable logs"*

When a deferred item is specified, it moves from Deferred table to the appropriate tier (checked).

### 6. spec-system.md Updates

Add to README.md update rules:

```
- `/spec.init` creates roadmap.md with inferred feature backlog
- `/spec.specify` checks matching roadmap items + adds deferred splits
- `/spec.propose` reads roadmap.md including Deferred section (read-only)
```

Add to artifact directory listing:

```
### roadmap.md — Feature Backlog

Persistent backlog of specs to build, organized in tiers (MVP / Post-MVP / Future) with a Deferred section for items split from `/spec.specify` requests. Generated by `/spec.init`, maintained by `/spec.specify`.
```

### 9. Definition of Done Updates

**`/spec.init`:**
- `[ ] roadmap.md exists with at least 1 inferred item per populated tier`

**`/spec.specify`:**
- `[ ] If `.specs/roadmap.md` exists: matching item checked OR no match (skip)`
- `[ ] If split performed: deferred items added to roadmap.md Deferred section`

---

### 10. Edge Cases

| Case | Behavior |
|------|----------|
| No roadmap.md (legacy project) | All roadmap operations skip silently. `/spec.propose` uses AI inference (current behavior) |
| User creates roadmap.md manually | Fully compatible — same format |
| Duplicate items | Before adding deferred, check unchecked items in tiers. If match exists, enrich context instead of duplicating |
| Empty tiers at init | Leave with `> No items yet.` hint. Valid — not every project has clear long-term features |
| `--auto` flag on init | Roadmap generated with AI inference, no user review |
| `--dry-run` flag on init | Roadmap listed in output but not created |
| Deferred item later specified | Move from Deferred table to appropriate tier (checked + linked) |

### 12. What This Does NOT Change

- No new commands created
- No changes to `/spec.plan`, `/spec.implement`, `/spec.check`, `/spec.feature`, `/spec.refine`
- No changes to the feature spec format (spec.md)
- No changes to the plan format (plan.md)
- No changes to the changelog format
- `/spec.propose` remains read-only (does not write to roadmap.md)
